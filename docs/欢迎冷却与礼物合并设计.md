# 欢迎冷却与礼物合并设计

> 状态：待实现。本文约束第一版行为；实现后把差异记到文末「实现偏差」。
>
> 依赖基础：6110 进场、6501 礼物、领域事件总线去重、welcome / gift_thank 独立模块、统一弹幕队列。
>
> 不改变事件来源：仍只消费页面 TAF，不改 WebSocket，不改 `event_id` 去重。

## 1. 目标

把「达标立刻发一条」改成「同一人短时间只欢迎一次、同一种礼物连击只感谢一次」。

必须满足：

- 贵族刷新、断线重进、反复进出，冷却时间内不再欢迎。
- 同一人连点同一种礼物，窗口结束后只入队一条感谢，数量和金额按窗口合计。
- 门槛、模板、发送失败不重试、三级优先级都不改。
- 冷却表和合并窗口只存在本场内存，不写入 `config/app.json`。
- 关闭发送、关闭对应模块或停止挂房时，未结算的礼物窗口直接丢弃，不补发。

第一版不做：普通用户进场欢迎、大额情感加深、多套随机文案、跨礼物合并、关键词回复、把冷却或窗口持久化到磁盘。

## 2. 现状

| 路径 | 现在 | 问题 |
| --- | --- | --- |
| `welcome.consider` | 每次达标 `enter` 立刻 `submit` | 6110 在刷新、重进时会再推，同一 uid 连着欢迎 |
| `gift_thank.consider` | 每个 6501 包过门槛立刻 `submit` | 总线按 `order_id` 去重只挡官方重复回调；连击是多个新订单，会拆成多条感谢 |
| `bus.event_id_for` | 礼物优先 `order:{strPayId}` | 正确，合并不能改这一层 |

一包里 `count > 1` 已经按数量填模板，不是本设计的缺口。本设计只合并「同一个人、同一种礼物、连续多包」。

## 3. 用户流程

```text
打开「自动场控」
  → 进场欢迎：门槛和文案照旧，增加「同一人几分钟内不重复欢迎」，默认 5 分钟，0 为关闭
  → 礼物感谢：金额门槛和文案照旧，增加连击静默窗口和最长等待，默认 3 秒 / 8 秒；静默为 0 则不合并
  → 开启对应模块和「允许发送」
  → 启动场控
```

主播不需要理解窗口状态机。WebUI 不展示冷却表或未结算窗口。

## 4. 配置

沿用各模块 schema 画表单。时间字段与弹幕间隔相同：配置里存毫秒，WebUI `type=seconds`。

### 4.1 进场欢迎

| 键 | 类型 | 默认 | 含义 |
| --- | --- | --- | --- |
| `cooldown_ms` | seconds | `300000`（5 分钟） | 同一 uid 两次欢迎的最短间隔。`0` 关闭冷却，行为与现在相同 |

原有 `enabled`、`min_noble_level`、`min_consume_level`、`template` 不变。旧 `app.json` 没有该键时，与默认配置深合并后即为 5 分钟。

### 4.2 礼物感谢

| 键 | 类型 | 默认 | 含义 |
| --- | --- | --- | --- |
| `merge_quiet_ms` | seconds | `3000` | 同人同礼物静默这么久后结算。`0` 关闭合并，每包立刻判断 |
| `merge_max_ms` | seconds | `8000` | 窗口从第一包起最长等待。到点强制结算，之后的包开新窗口 |

约束：

- `merge_quiet_ms == 0`：不合并，忽略 `merge_max_ms`。
- `merge_max_ms < merge_quiet_ms`：按 `merge_quiet_ms` 计最长等待。
- `merge_max_ms == 0` 且静默大于 0：最长等待等于静默时间。

原有金额门槛和模板不变。门槛在窗口结算时用**合计**判断，不在入窗时判断。

## 5. 欢迎冷却

### 5.1 流程

```text
enter
  → 模块关闭 → 忽略
  → 无守护且贵族/消费不达标 → 忽略
  → cooldown_ms == 0 → 直接入队
  → uid 无效 → 无法冷却，直接入队（与现有测试事件兼容）
  → 该 uid 距上次决定欢迎不足 cooldown_ms → 只记日志，不入队
  → 否则记下 now，再 submit
```

冷却从**决定欢迎并 `submit`** 起算，不等发送成功。发送失败不重试；若等发送成功再记冷却，高峰漏发后对方再进会立刻再欢迎，队列更容易堆积。

### 5.2 状态

本场内存表：

```text
uid（字符串） → monotonic 时间
```

- 键必须是 6110 的 `uid`，不能用昵称。
- 不持久化。停止挂房或更换房间时清空。
- TAF 重挂房不清空：仍是同一场。
- 进程重启自然清空。
- 第一版不对帝皇、至尊或守护开绿灯。身份再高，冷却内刷进出也不欢迎。
- 冷却只挡 `enter`。进场被欢迎后开通守护、超粉、贵族，仍走各自感谢模块。

### 5.3 日志

- 冷却命中：`welcome 冷却中，忽略 {nick}（uid={uid}，剩余约 Ns）`
- 其余沿用现有达标 / 忽略日志。

## 6. 礼物连击合并

### 6.1 和总线去重的关系

```text
6501 TAF
  → bus 按 order_id 去重（官方重复回调）
  → gift_thank.consider
       → 0 元：不入窗、不感谢
       → 关闭合并：按现行单包门槛立刻 submit
       → 开启合并：写入窗口，等 tick 结算
```

`strPayId` 去重不能拿来当连击合并。连击是多个新订单。

### 6.2 合并键

```text
sender_uid + item_id
```

只合并同一个人、同一种礼物。火箭和飞机分开；两个人同时送也不并。

`item_id` 缺失时退回 `item_name`。uid 与礼物标识都缺失时不合并，按单包立刻处理。

守护、超粉、贵族不进入礼物窗口。

### 6.3 窗口

```text
pending[(uid, item_key)] = {
  nick, item_name, item_id,
  count,          # 累加
  value_fen,      # 累加
  first_at, last_at,
  first_event_id
}
```

昵称取窗口内最后一包，给 `{nick}` 用。

时间：

- **静默**：`now - last_at >= merge_quiet_ms` → 结算。
- **最长等待**：`now - first_at >= merge_max_ms` → 强制结算，后续包开新窗口。

有人一直连点时，不能无限拖延感谢。

### 6.4 入窗与结算

入窗：

- 模块关闭：忽略，与现在相同。
- `value_fen <= 0`：不入窗。
- 其它包（含低于金额门槛的）都入窗。第一包 3 毛、连击后超过 6 元门槛时，应能合并后感谢。

结算：

```text
count = max(1, 窗口 count)
合计金额、单价（合计 ÷ 数量）都过线
  → 按现有模板 submit 一条
     {count} / {value_yuan} 用窗口合计
     event_id = merge:{uid}:{item_key}:{first_event_id}
     reason 带合计数量和金额
  → 否则整波丢弃，记低于门槛
```

单价与现在单包公式一致：`合计分 / 数量`，再和 `min_unit_value_fen` 比。

窗口期间**不要** `submit`，也不去改已经在发送队列里的正文。队列没有按 `event_id` 更新文案的能力。

### 6.5 调度

礼物合并需要定时结算，不能只靠下一条礼物。

- 独立小对象，类似 `novel_player`：`consider()` 只更新窗口，`tick()` 结算到期窗口。
- 由 `RoomSupervisor._sender_loop` 在 `novel_player.tick()` 旁调用。
- 有未结算窗口时，发送循环按约 200ms 醒来，不要空闲睡满 1 秒，以免 3 秒静默被拖成 4 秒。
- `tick()` 内读当时配置。运行中把静默改成 0：下一拍把现有窗口按单包规则立刻结算（已入窗的合计仍按窗口，不拆回多条）。
- 不使用 `threading.Timer`，避免和工人线程、停止挂房竞态。

### 6.6 丢弃，不补发

下列情况清空全部窗口且不 `submit`：

- 停止挂房
- `LU 关闭 发送` 或 WebUI 关闭「允许发送」
- `LU 关闭 感谢` 或关闭 `gift_thank`
- 更换房间

`tick()` 若发现发送总开关或礼物模块已关闭，也丢弃窗口。避免关感谢后仍把积压连击打出去。

TAF 重挂房不丢窗口：连击可能跨过短暂重进。

## 8. 日志与测试

### 8.1 日志

不打印完整礼物/进场原始包。普通冷却忽略和窗口暂存只打 uid、昵称、礼物名、数量、金额、剩余秒数。

| 场景 | 日志要点 |
| --- | --- |
| 冷却忽略 | 冷却中、uid、剩余秒 |
| 入窗 | 暂存连击、当前合计数量和分 |
| 结算感谢 | 沿用入队 / 已发送 |
| 结算未过门槛 | 连击合计低于门槛 |
| 丢弃窗口 | 原因（停止 / 关闭发送 / 关闭感谢）和丢弃条数 |

### 8.2 测试

欢迎：

- 同一 uid 冷却内两次进场，只入队一次。
- 冷却过后第二次入队。
- `cooldown_ms=0` 两次都入队。
- 不同 uid 互不影响。
- 无 uid 的事件不冷却（现有单测事件可继续用）。
- 守护绕过贵族门槛的逻辑不变；冷却仍按 uid 生效。

礼物：

- 同人同礼物两包在静默内，结算一条，`count` 和金额为合计。
- 不同 `item_id`、不同 uid 不合并。
- 第一包低于合计门槛、两包合计过线，结算一条。
- 合计仍低于门槛，不入队。
- 0 元不入窗。
- `merge_quiet_ms=0` 恢复每包立刻判断。
- 最长等待：窗口内持续补包，到 `merge_max_ms` 必须结算一次。
- 关闭模块或 `clear()` 等价路径后，待结算窗口不再入队。

时钟用可注入的 monotonic，不要 `sleep` 真实 3 秒。

## 10. 明确不做

- 不按昵称冷却或合并。
- 不把不同礼物合成「感谢 xxx 送礼」。
- 不把守护/贵族/超粉并进礼物窗口。
- 不在发送队列里改已入队文案。
- 不把冷却或窗口写入配置或日志文件。
- 不为冷却或合并增加 LU 指令。
- 不因合并回退到 WebSocket，也不放宽 0 元礼物。

## 12. 实现偏差

2026-09-01 实现，与设计的差异（均为实现细节，不改变行为约束）：

- `GiftMerger.tick()` 增加可选参数 `config` / `send_enabled`：默认仍读 `config_store`，单测可直接注入配置，避免碰磁盘配置。
- 合并窗口把提交目标 `danmaku` 对象存进 pending 项（设计只写共享单例）；结算时向入窗时的对象提交，单测可用 FakeDanmaku 验证。
- 窗口 `item_key` 同时存入 pending 项，用于构造合并 `event_id`。
- `config_store.put_feature` / `set_features_enabled` 在关闭 `gift_thank` 或 `danmaku` 时延迟导入并调用 `merger.reset()`，覆盖 WebUI 保存路径；LU 指令走 `set_features_enabled`，自动被同一钩子覆盖，remote_control 不需单独接线。
- 运行中把静默改成 0 的场景由 `tick()` 内 `quiet_s <= 0` 时所有窗口立即到期实现（设计 §6.5 的"按单包规则立刻结算"解读为：已入窗的合计仍按窗口结算成一条，与 §6.5 一致）。
