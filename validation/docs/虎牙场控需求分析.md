# 虎牙直播间 URI 事件监控需求分析

> **验证期文档。** 产品需求见 [../../docs/场控产品需求.md](../../docs/场控产品需求.md)。本文仍约束「事件只能来自页面 URI、发送走输入框」；其中「不做 WebUI / 不做自动感谢」已被 D-001b、D-004b 取代。

## 1. 文档目的

本文档定义项目当前唯一有效的事件监控路线：程序通过正常浏览器会话进入指定虎牙直播间，获取页面已经接收的原始事件包，以 `uri` 分发并按对应结构解码。

`Event.png` 是候选映射。URI 通道、结构名和字段必须由用户用真实会话验证后，才能视为已确认。不得使用页面文案关键词、CSS class、HTML 正则或 `MutationObserver` 采集业务事件。

## 2. 项目目标

项目需要验证并形成以下能力：

1. 浏览器登录状态能够通过持久化 Profile 保留。
2. 打开指定直播间后，能够稳定获得包含 URI 的原始事件包。
3. 能够识别七类候选 URI，并将载荷解码为结构化字段。
4. 原始事件与标准化事件均可记录、诊断和离线回放。
5. 刷新、断线或重连后能够恢复采集，并记录可能的丢失区间。
6. 用户人工确认后能够通过正常输入框发送一次测试弹幕。

当前面向单账号、单房间的能力验证，不是完整的无人值守场控产品。

**当前里程碑**只要求第 1、2 项和第 6 项可用，以及第 2 项的现场验证。结构解码（第 3 项）在 URI 验证通过之后进行。

## 3. 候选 URI

| URI | 结构名 | 统一事件类型 | 含义 | 确认状态 |
| ---: | --- | --- | --- | --- |
| 1400 | `MessageNotice` | `chat` | 弹幕 | 已出现；解码未做 |
| 6110 | `VipEnterBanner` | `enter` | 贵族进场横幅 | 产品进场主路径，见 `贵族进场解析.md` |
| 6111 | 待确认 | （不产出 `enter`） | 普通用户进场 | 已出现；产品只要贵族 |
| 1005 | `NobleEnterNotice` | `enter` | 贵族进场通知 | 001–006 未出现 |
| 6200 | `EnterPushInfo` | `enter` | 进场推送 | 001–006 未出现 |
| 6501 | `SendItemSubBroadcastPacket` | `gift` | 礼物 | 002 已出现；金额见 `礼物解析.md` |
| 8006 | `AttendeeCountNotice` | `attendee_count` | 人气值 | 待现场验证 |

URI 6111 的结构名未在图中给出。当前产品不把它标准化为 `enter`。贵族进场字段见 `贵族进场解析.md`。

## 4. 范围

### 4.1 包含

- 启动可见 Chromium 并使用独立持久化 Profile。
- 用户手工处理登录、验证码和安全验证。
- 通过房间号或 URL 打开一个已开播的指定直播间。
- 挂接页面已经建立的事件通道，获取原始事件信封和载荷。
- 按 URI 分发已知事件，记录未知 URI。
- 对七类候选 URI 建立解码器和离线回放测试（验证通过后）。
- 将不同结构标准化为统一事件模型。
- 分开保存原始日志、标准化日志和通道状态日志。
- 页面刷新、导航、断线和重连后的恢复与诊断。
- 人工确认后发送一次测试弹幕。

### 4.2 不包含

- 从 DOM 节点、页面文字、CSS class、ARIA 或局部 HTML 推断业务事件。
- 使用 DOM 作为 URI 采集失败时的程序兜底。
- 另建独立弹幕连接，或扫描与页面通道无关的接口。
- 自动监控主播何时开播。
- 自动进入多个直播间、多账号管理或长期无人值守。
- 自动感谢、连续礼物合并、复杂规则、发送冷却和排队。
- 绕过平台登录、安全验证、权限或频率限制。
- FastAPI、Web 管理界面、SQLite、托盘、安装包和自动更新。

## 5. 目标架构

### 5.1 会话层

Playwright 负责启动带持久化 Profile 的浏览器、打开房间和维持正常页面会话。登录失效时明确提示用户，不自动高频重试。

### 5.2 通道挂接层

在页面正常接收事件的路径上建立只读挂接，输出原始事件信封。当前实现观察页面自己的 WebSocket，并尝试读取页面 `TafMx.UriMapping`。具体挂接点以现场验证为准。业务层不得依赖页面渲染结果。

通道层至少提供：会话标识、房间标识、事件接收时间、URI、原始载荷及编码信息、通道建立/关闭/错误/重连状态。

### 5.3 URI 路由层

路由器只根据事件信封中的 URI 选择解码器：

- 已知 URI 交给对应结构解码器。
- 未知 URI 记录为 `unknown`，不得丢弃或按页面文案猜测。
- URI 存在但载荷异常时记录 `decode_error`，监控循环继续运行。

当前里程碑只做到“提取 URI 并记录”，不进入解码器。

### 5.4 结构解码层

每个 URI 解码器独立实现，输入原始载荷，输出结构字段和解码状态。解码器应能在没有浏览器的情况下读取保存的样本执行测试。不得静默兼容不认识的结构版本。

### 5.5 标准化层

不同 URI 的结果统一为 `chat`、`enter`、`gift`、`attendee_count` 或 `unknown`。标准化层不负责重新读取 DOM。

### 5.6 输出层

至少分开保存：

1. 原始事件日志：证据保留、重新解码和版本适配。
2. 标准化事件日志：业务规则、统计和人工验收（解码阶段）。
3. 通道状态日志：断线、重连和可能的漏报区间。

## 6. 功能要求

### 6.1 登录与房间访问

- 使用独立 Profile 目录保存登录状态。
- 首次登录和安全验证由用户手工完成。
- 支持 `--room` 或 `--url` 指定一个直播间。
- 页面会话未建立或登录状态无效时不得开始测试发送。

### 6.2 原始事件采集

- 采集必须发生在页面已有事件通道上。
- 原始记录必须包含 URI，不以渲染文本代替。
- 载荷以可无损回放的形式保存，并记录编码名称。
- 写入应及时刷新。
- 同一原始包不得因多个消费者被重复写入且无法识别。

### 6.3–6.6 弹幕 / 进场 / 礼物 / 人气

URI 验证通过后再按结构解码。最低字段要求：

- 弹幕 1400：发送者标识、昵称、正文。
- 进场：当前产品只要贵族。标准化 `enter` 只来自 URI 6110。最低字段：用户标识、昵称、来源 URI、贵族名、消费等级、有无守护。路径见 `贵族进场解析.md`。6111 为普通进场，不产出 `enter`。1005 / 6200 本批未出现，不作为主通道。
- 礼物 6501：送礼人、礼物标识或名称、数量、本包金额（tag `41`，分）。小额（虎粮、磁铁等）不进入感谢；门槛看金额，不看礼物名。见 `礼物解析.md`。
- 开通守护 6540：房间横幅，作为独立感谢事件，不走礼物金额门槛。同一秒的 1400 系统句不重复感谢。见 `守护开通解析.md`。
- 人气 8006：人气数值。不得把人气值说成真实在线人数，除非另有证据。

### 6.7 测试弹幕发送

- 仅使用正常页面输入框和发送按钮。
- 每次发送前必须获得用户明确确认。
- 发送能力与事件采集能力分别验收。
- 发送失败不得高频自动重试。

## 7. 日志模型

原始事件日志建议字段：`schema_version`、`run_id`、`session_id`、`room_id` / `room_url`、`uri`、`struct_name`、`received_at`、`payload_encoding`、`raw_payload`、`raw_fingerprint`。

标准化事件日志通用字段：`event_type`、`event_id`、`page_timestamp`、`decode_status`、`decode_error`、`data`。

原始载荷可能包含用户标识，不得默认提交仓库。

## 8. 验证流程

1. 使用持久化 Profile 启动浏览器并登录。
2. 打开一个明确授权、已经开播的测试房间。
3. 运行 `capture`，确认原始记录中出现 URI。
4. 对照页面 `TafMx.UriMapping`（若出现）和 `Event.png`。
5. 分别等待弹幕、进场、礼物、人气；记录哪些 URI 出现。
6. 人工将页面可见结果与 URI 日志对照；页面只作验收证据。
7. 刷新页面后确认挂接恢复。
8. 关闭并重启程序后重复测试。
9. URI 验证通过后，再用保存的原始包做解码器测试。
10. 人工确认后发送一次测试弹幕。

## 9. 验收标准

### 9.1 当前里程碑：原始采集

- 真实会话中能解析出 URI，进程不因未知包退出。
- 每条原始记录包含 URI（或明确的信封解析失败原因）、原始载荷、房间、会话和接收时间。
- 七类候选 URI 均有结论：出现 / 本场未触发 / 页面映射没有。
- 页面刷新后能够恢复采集。

### 9.2 后续：结构解码与事件验收

- 每个要落地的 URI 有独立解码器和离线回放测试。
- 弹幕、贵族进场、礼物至少各三轮对照。进场不要求普通用户。
- 人气验证 URI 8006 的数值更新。

### 9.3 测试发送

- 人工确认后成功发送一次测试弹幕，或保留明确失败证据。
- URI 事件不得自动触发发送。

## 10. 风险与处理

- 同一 URI 的载荷结构可能随页面版本变化。原始包必须保留。
- 6110、6111、1005、6200 可能业务重叠。已有样本：贵族只出 6110，普通人出 6111；1005/6200 未出现。产品 `enter` 只消费 6110。
- 刷新或通道重连期间可能漏报，通道日志记录断开和恢复时间。
- 持久化 Profile 会过期。登录异常交由用户处理。
- 原始事件含用户标识，必须控制保存期限和访问范围。

## 11. 待确认事项

1. 真实测试房间、账号授权和测试负责人。
2. 页面事件通道在本机会话中是否就是 WebSocket + `WSPushMessage.iUri`。
3. 各结构的编码、字段定义和版本标识。
4. URI 6111 的准确结构名。
5. 多个进场 URI 的重复关系。
6. 小额礼物预算。
7. 捕获率等阈值。
8. 原始载荷保存期限、脱敏和访问范围。
9. 是否后续单独增加主播开播状态监控。

## 12. 后续路线

URI 采集验证通过后，再依次考虑：解码器、去重和礼物合并、感谢规则、开播状态监控、多房间和长期运行、数据库与界面。

## 13. 总体结论

项目从“验证网页是否显示事件”转向“消费页面事件通道中的 URI”。当前工作是让你在真实房间里确认这条通道，而不是维护 DOM 样本，也不是立刻实现全部结构解码。
